== Description

Every production workload MUST have documented Service Level Objectives (SLOs) and Service Level Agreements (SLAs). SLOs must define availability, latency, error rate, and throughput targets with explicit measurement windows. SLAs must reference SLOs and define consequences of non-compliance. Both documents must be version-controlled, reviewed quarterly, and linked to monitoring dashboards with automated alerting when error budgets are consumed.

== Rationale

[cols="1,3"]
|===
|Risk |Description

|*Risk* |Workloads without documented SLOs cannot measure or communicate user impact.

|*Risk* |Missing availability targets lead to inconsistent expectations between teams and stakeholders.

|===

== Requirements

* Every production workload MUST have documented Service Level Objectives (SLOs) and Service Level Agreements (SLAs).
* SLOs must define availability, latency, error rate, and throughput targets with explicit measurement windows.
* SLAs must reference SLOs and define consequences of non-compliance.
* Both documents must be version-controlled, reviewed quarterly, and linked to monitoring dashboards with automated alerting when error budgets are consumed.

== Implementation Guidance

1. Document the requirement in a version-controlled policy or standard.
2. Assign ownership and establish a review cadence (e.g., quarterly).
3. Implement the required configuration as code in Terraform or equivalent IaC.

== Checks

=== waf-rel-010.tf.aws.cloudwatch-slo-alarm

*Engine:* `terraform` | *Provider:* aws | *Automated:* Yes

*AWS CloudWatch alarm must be configured for SLO availability monitoring*

An Amazon CloudWatch alarm must be defined to track availability and trigger when the error rate exceeds the SLO threshold. This acts as the automated enforcement of the SLO monitoring requirement.

*Scope:* `resource` — `aws_cloudwatch_metric_alarm`

*Assertions:*
* `alarm_name` not empty — CloudWatch alarm must have a descriptive name.
* `metric_name` not empty — CloudWatch alarm must specify the metric to monitor.
* `alarm_actions` not empty — CloudWatch alarm must have at least one action configured.
* `threshold` attribute exists — CloudWatch alarm must define a threshold value.

*Remediation:* Define a CloudWatch alarm that monitors the primary SLO metric (e.g., error rate, latency). Configure alarm_actions to notify SNS topics used by on-call rotation.

.Compliant

[source,terraform]
----
resource "aws_cloudwatch_metric_alarm" "slo_error_rate" {
  alarm_name          = "slo-payment-service-error-rate"
  comparison_operator = "GreaterThanThreshold"
  evaluation_periods  = 5
  metric_name         = "5XXError"
  namespace           = "AWS/ApiGateway"
  period              = 60
  statistic           = "Sum"
  threshold           = 10
  alarm_description   = "SLO: error rate > 0.1% over 5 minutes"
  alarm_actions       = [aws_sns_topic.oncall.arn]
  ok_actions          = [aws_sns_topic.oncall.arn]
  treat_missing_data  = "notBreaching"
}
----

.Non-Compliant

[source,terraform]
----
resource "aws_cloudwatch_metric_alarm" "error_alarm" {
  alarm_name          = "errors"
  comparison_operator = "GreaterThanThreshold"
  evaluation_periods  = 1
  metric_name         = "Errors"
  namespace           = "AWS/Lambda"
  period              = 300
  statistic           = "Sum"
  threshold           = 100
  # Missing: alarm_actions – no one is notified
}
----

=== waf-rel-010.tf.azurerm.monitor-metric-alert-slo

*Engine:* `terraform` | *Provider:* azurerm | *Automated:* Yes

*Azure Monitor metric alert must be configured for SLO monitoring*

An Azure Monitor metric alert must be configured for each production workload to track availability and latency against SLO targets.

*Scope:* `resource` — `azurerm_monitor_metric_alert`

*Assertions:*
* `name` not empty — Monitor alert must have a descriptive name.
* `criteria` attribute exists — Monitor alert must define alert criteria.
* `action` attribute exists — Monitor alert must have at least one action group configured.

*Remediation:* Configure an azurerm_monitor_metric_alert with criteria referencing the SLO metric and an action block pointing to an azurerm_monitor_action_group that notifies on-call.

.Compliant

[source,terraform]
----
resource "azurerm_monitor_metric_alert" "slo_availability" {
  name                = "slo-api-availability"
  resource_group_name = azurerm_resource_group.main.name
  scopes              = [azurerm_application_insights.main.id]
  description         = "SLO: availability < 99.9%"
  severity            = 1
  criteria {
    metric_namespace = "microsoft.insights/components"
    metric_name      = "availabilityResults/availabilityPercentage"
    aggregation      = "Average"
    operator         = "LessThan"
    threshold        = 99.9
  }
  action {
    action_group_id = azurerm_monitor_action_group.oncall.id
  }
}
----

.Non-Compliant

[source,terraform]
----
resource "azurerm_monitor_metric_alert" "alert" {
  name                = "alert"
  resource_group_name = azurerm_resource_group.main.name
  scopes              = [azurerm_application_insights.main.id]
  criteria {
    metric_namespace = "microsoft.insights/components"
    metric_name      = "requests/failed"
    aggregation      = "Count"
    operator         = "GreaterThan"
    threshold        = 100
  }
  # Missing: action – no notification configured
}
----

=== waf-rel-010.tf.google.monitoring-alert-policy-slo

*Engine:* `terraform` | *Provider:* google | *Automated:* Yes

*GCP Monitoring alert policy must be configured for SLO tracking*

A Google Cloud Monitoring alert policy must be configured to track SLO compliance and notify on-call when error budget burn rate exceeds thresholds.

*Scope:* `resource` — `google_monitoring_alert_policy`

*Assertions:*
* `display_name` not empty — Alert policy must have a descriptive display name.
* `conditions` not empty — Alert policy must define monitoring conditions.
* `notification_channels` not empty — Alert policy must have notification channels configured.

*Remediation:* Define a google_monitoring_alert_policy with conditions referencing the SLO metric and notification_channels pointing to configured channels (PagerDuty, email, etc.).

.Compliant

[source,terraform]
----
resource "google_monitoring_alert_policy" "slo_burn_rate" {
  display_name = "SLO Error Budget Burn Rate – Payment API"
  combiner     = "OR"
  conditions {
    display_name = "Fast burn: >14x for 1h"
    condition_threshold {
      filter          = "select_slo_burn_rate(\"projects/${var.project}/services/payment-api/serviceLevelObjectives/availability\", 3600)"
      comparison      = "COMPARISON_GT"
      threshold_value = 14.4
      duration        = "0s"
    }
  }
  notification_channels = [google_monitoring_notification_channel.oncall.name]
  alert_strategy {
    notification_rate_limit { period = "300s" }
  }
}
----

.Non-Compliant

[source,terraform]
----
resource "google_monitoring_alert_policy" "errors" {
  display_name = "Errors"
  combiner     = "OR"
  conditions {
    display_name = "Error count"
    condition_threshold {
      filter          = "metric.type=\"logging.googleapis.com/user/errors\""
      comparison      = "COMPARISON_GT"
      threshold_value = 100
      duration        = "60s"
    }
  }
  # Missing: notification_channels – alert fires silently
}
----

=== waf-rel-010.tf.stackit.availability-slo-defined

*Every production workload for stackit*

Every production workload must be documented in IaC via a availability-slo-defined tag/label on stackit_project. This validates the control is tracked as code.
