= WAF-SUS-030 – Green Region & Carbon-Aware Workload Placement
:page-toc: right
:control-id: WAF-SUS-030
:pillar: sustainability
:severity: medium
:category: data-governance
:automatable: High
:description: Workloads without strict data-residency requirements MUST consider carbon intensity of cloud regions in placement decisions. When architectural and regulatory constraints allow, workloads SHOULD be placed in regions with high renewable energy mix or low grid carbon intensity. Region selection decisions MUST document sustainability considerations alongside latency and cost factors. Batch workloads with flexible placement MUST evaluate green region alternatives.

[.metadata]
*Säule:* Sustainability | *Schweregrad:* Mittel | *Kategorie:* Data Governance | *Automatisierbar:* High

== Beschreibung

Workloads without strict data-residency requirements MUST consider carbon intensity of cloud regions in placement decisions. When architectural and regulatory constraints allow, workloads SHOULD be placed in regions with high renewable energy mix or low grid carbon intensity. Region selection decisions MUST document sustainability considerations alongside latency and cost factors. Batch workloads with flexible placement MUST evaluate green region alternatives.

== Begründung

[cols="1,3"]
|===
|Risiko |Beschreibung

|*Risk* |Data may leave approved jurisdictions and violate regulatory requirements.

|*Risk* |Vendor lock-in reduces future portability and sovereignty options.

|===

== Anforderungen

* Workloads without strict data-residency requirements MUST consider carbon intensity of cloud regions in placement decisions.
* When architectural and regulatory constraints allow, workloads SHOULD be placed in regions with high renewable energy mix or low grid carbon intensity.
* Region selection decisions MUST document sustainability considerations alongside latency and cost factors.
* Batch workloads with flexible placement MUST evaluate green region alternatives.

== Implementierungsleitfaden

1. Document the requirement in a version-controlled policy or standard.
2. Assign ownership and establish a review cadence (e.g., quarterly).
3. Implement the required configuration as code in Terraform or equivalent IaC.

== Checks

=== waf-sus-030.tf.aws.preferred-regions

*Engine:* `terraform` | *Provider:* aws | *Automated:* Ja

*AWS provider region should be a low-carbon-intensity region*

This check validates that the AWS provider is configured to use a region with known high renewable energy mix. High-carbon regions are flagged as warnings to trigger documentation of the sustainability justification.

*Scope:* `provider` — `aws`

*Assertions:*
* `region` in `['us-west-2', 'eu-north-1', 'eu-west-1']` — AWS region has a high carbon intensity. Consider us-west-2, eu-north-1, eu-west-1 for lower emissions.

*Remediation:* If workloads can be placed in a lower-carbon region without violating data residency, latency, or compliance requirements, prefer: us-west-2 (Oregon, ~89% renewable), eu-north-1 (Stockholm, ~95% renewable), eu-west-1 (Ireland, ~80% renewable). If high-carbon region is required, document the justification in an ADR and offset through RECs for that region's workload footprint.

.Compliant

[source,terraform]
----
provider "aws" {
  region = "eu-north-1"  # Stockholm – ~95% renewable energy
  # Sustainability justification: low carbon intensity region selected per WAF-SUS-030
}
----

.Non-Compliant

[source,terraform]
----
provider "aws" {
  region = "ap-east-1"  # Hong Kong – high carbon intensity grid
  # WAF-SUS-030 Warning: document carbon justification or migrate to lower-carbon region
}
----

=== waf-sus-030.tf.google.preferred-regions

*Engine:* `terraform` | *Provider:* google | *Automated:* Ja

*GCP provider region should be a low-carbon-intensity region*

GCP regions vary significantly in carbon intensity. europe-north1 (Finland) and europe-west1 (Belgium) are among the lowest carbon-intensity regions globally.

*Scope:* `provider` — `google`

*Assertions:*
* `region` in `['europe-north1', 'europe-west1', 'us-west1']` — GCP region has elevated carbon intensity. Consider europe-north1, europe-west1, or us-west1.

*Remediation:* For GCP workloads, prefer europe-north1 (Finland, ~97% renewable), europe-west1 (Belgium), or us-west1 (Oregon). GCP Carbon Footprint dashboard shows per-project emissions by region. Use carbon-free energy percentage (CFE%) metric available in GCP Sustainability console.

.Compliant

[source,terraform]
----
provider "google" {
  project = var.project_id
  region  = "europe-north1"  # Finland – 97% carbon-free energy
}
----

.Non-Compliant

[source,terraform]
----
provider "google" {
  project = var.project_id
  region  = "asia-east1"  # Taiwan – lower renewable energy share
  # WAF-SUS-030 Warning: document carbon justification
}
----

=== waf-sus-030.tf.azurerm.preferred-regions

*Engine:* `terraform` | *Provider:* azurerm | *Automated:* Ja

*Azure provider location should be a low-carbon-intensity region*

Azure regions differ in their carbon intensity. Sweden Central, Norway East, and North Europe (Ireland) consistently show the lowest carbon intensity in Azure's Emissions Impact Dashboard.

*Scope:* `resource` — `azurerm_resource_group`

*Assertions:*
* `location` in `['swedencentral', 'norwayeast', 'northeurope']` — Azure region may have elevated carbon intensity. Consider swedencentral, norwayeast, or northeurope.

*Remediation:* For Azure, prefer swedencentral (Sweden, ~95% renewable), norwayeast (Norway, hydro-powered), or northeurope (Ireland). Review Azure Emissions Impact Dashboard for current carbon intensity by region. Document sustainability rationale when using other regions.

.Compliant

[source,terraform]
----
resource "azurerm_resource_group" "main" {
  name     = "rg-app-prod"
  location = "swedencentral"  # Sweden – ~95% renewable energy
  tags = {
    sustainability-region = "green"
  }
}
----

.Non-Compliant

[source,terraform]
----
resource "azurerm_resource_group" "main" {
  name     = "rg-app-prod"
  location = "eastasia"
  # WAF-SUS-030 Warning: high carbon intensity region, document justification
}
----

=== waf-sus-030.tf.stackit.renewable-energy-used

*Engine:* `terraform` | *Provider:* stackit | *Automated:* Ja

*Workloads without strict data-residency requirements for stackit*

Workloads without strict data-residency requirements must be documented in IaC via a renewable-energy-used tag/label on stackit_project. This validates the control is tracked as code.

*Scope:* `resource` — `stackit_project`

*Assertions:*
* `labels` key exists — stackit_project is missing the renewable-energy-used tag/label.

*Remediation:* Add a renewable-energy-used tag/label to the stackit_project resource to show the stackit implementation of WAF-SUS-030 is tracked in IaC.

.Compliant

[source,terraform]
----
resource "stackit_project" "example" {
  labels = {
    renewable-energy-used = "true"
  }
}
----

.Non-Compliant

[source,terraform]
----
resource "stackit_project" "example" {
  # Missing renewable-energy-used labels
}
----
