# Agent Guidelines for WAF++ Framework Repository

This repository contains the **WAF++** (Well-Architected Framework++) documentation – a community-driven framework for sovereign, cloud-agnostic cloud engineering. The documentation is built using **Antora**, a multi-repository documentation site generator that produces documentation from AsciiDoc files.

## Project Overview

**Repository**: https://github.com/WAF2p/framework.git  
**Language**: English  
**Type**: Antora Documentation Component  
**Build System**: Antora 3.1.x  
**Content Focus**: Cloud architecture, governance, security, cost optimization, reliability, sustainability, sovereign, and agentic AI  
**Output Format**: Static HTML generated by Antora

## Build/Test Commands

This repository is consumed by Antora as a documentation component. The build happens in the parent website repository (`waf2p.github.io`), not directly here.

### Local Development

**Note**: This repository does not build standalone. It is sourced by Antora from the website repository. Content can still be validated locally.

**Preview AsciiDoc files**:
```bash
# Using asciidoctor (if installed)
asciidoctor modules/ROOT/pages/index.adoc -o /tmp/preview.html
open /tmp/preview.html

# Or online: https://asciidoclive.com/
```

**Validation**:
```bash
# Find all AsciiDoc files
find modules -name "*.adoc" -type f

# Check navigation
cat modules/ROOT/nav.adoc
cat modules/pillar-security/nav.adoc

# Find broken or relative xrefs
grep -R "xref:\.\." modules --include="*.adoc"
```

### Building with Antora

To build the complete documentation site including this component:

```bash
# Use the website repository
cd /path/to/waf2p.github.io

# Build with local filesystem source
npx antora antora-playbook-local.yml

# Or use the Taskfile
task docs:build:local
```

### Testing Individual Files

```bash
# Read file content
cat modules/pillar-security/pages/index.adoc

# Check document structure
head -20 modules/pillar-security/pages/index.adoc
```

## Content Style Guidelines

### Language & Tone

- **Primary language**: English – all documentation must be in English
- **Tone**: Professional, accessible, community-focused
- **Audience**: Architects, platform teams, security/compliance professionals
- **Style**: Clear, structured, action-oriented

### AsciiDoc Structure

**Page attributes** (top of each `.adoc` file):
```asciidoc
= Page Title
:description: Brief page description

Content starts here...
```

**Section Structure**:
- Use `= Title` for page title (H1, only once per page)
- Use `== Section` for main sections (H2)
- Use `=== Subsection` for subsections (H3)
- Use `*bold*` for emphasis on key terms
- Use `* ` for unordered lists (bullet points)
- Use `NOTE:`, `TIP:`, `IMPORTANT:`, `WARNING:`, `CAUTION:` for callouts

**Link Style**:
```asciidoc
# Internal cross-references within the same module
xref:controls.adoc[Controls]

# Cross-references across modules
xref:pillar-security:controls.adoc[Security Controls]
xref:pillar-agentic:index.adoc[Agentic Pillar]
xref:controls:catalog.adoc[Controls Catalog]

# External links
https://example.com[Link text^]

# Links with attributes
link:https://example.com[Link text,window=_blank]
```

**Example AsciiDoc Page**:
```asciidoc
= Security Pillar
:description: Security and compliance in the cloud

== What is it about?

The Security pillar addresses...

=== What is being done?

* Point 1
* Point 2

NOTE: Important hint for readers

== Further Information

See also xref:controls.adoc[Controls].
```

### Content Guidelines for Pillars

Each pillar should follow this structure:

1. **Definition & Scope** – What is covered?
2. **Principles** – 5-7 guiding principles
3. **Controls** – Measurable controls with ID, severity, automatability
4. **Best Practices** – Implementation guidance
5. **Maturity Model** – Maturity levels and self-assessment
6. **Evidence & Audit** – Evidence types and audit notes

### Naming Conventions

**Directories**:
- Lowercase with hyphens: `best-practices/`, `governance-community/`
- Pillar modules follow the pattern `pillar-<name>`

**Files**:
- Main content files: `index.adoc`
- All pages must use `.adoc` extension (AsciiDoc format)
- YAML controls in the controls module: `WAF-<PILLAR>-<NNN>.yml`

**Titles**:
- Pillars: "<Name> (Pillar: <Name>)" or "Pillar <Number> – <Name>"
- Controls: "WAF-<PILLAR>-<NNN> – <Title>"

### Navigation Structure

Each module has its own `nav.adoc`. The top-level navigation in `modules/ROOT/nav.adoc` links to the pillar landing pages:

```asciidoc
* xref:index.adoc[Home]
* xref:pillars/index.adoc[The 8 Pillars]
** xref:pillar-security:index.adoc[Security]
** xref:pillar-cost:index.adoc[Cost Optimization]
** xref:pillar-efficiancy:index.adoc[Performance Efficiency]
** xref:pillar-reliability:index.adoc[Reliability]
** xref:pillar-excellence:index.adoc[Operational Excellence]
** xref:pillar-sustainability:index.adoc[Sustainability]
** xref:pillar-sovereign:index.adoc[Sovereign]
** xref:pillar-agentic:index.adoc[Agentic]
* xref:controls:index.adoc[Controls]
```

Within a pillar, write links without a module prefix:
```asciidoc
** xref:controls.adoc[Controls (WAF-SEC)]
*** xref:controls/WAF-SEC-010.adoc[WAF-SEC-010]
```

**Key terms** (use consistently):
- **Pillar** = Pillar

- **Maturity/Maturity Model** = Maturity/Maturity Model
- **Governance** = Governance (keep English)
- **Cloud-agnostic** = Cloud-agnostic
- **Sovereign/Sovereignty** = Sovereign/Sovereignty
- **Agentic** = Agentic (domain term)

## Git Workflow

### Commit Message Format

Follow conventional commits style in English:

```
<type>: <description>

[optional body]

[optional footer]
```

**Types**:
- `feat`: New content or feature
- `fix`: Corrections to existing content
- `docs`: Documentation structure changes
- `style`: Formatting, typos (no content change)
- `refactor`: Content reorganization
- `chore`: Maintenance tasks

**Examples**:
```
feat: add Agentic pillar maturity model

fix: correct typo in security controls

docs: update navigation for 8 pillars
```

### Branch Strategy

- `main` - stable, production-ready content
- `feature/*` - new content or sections
- `fix/*` - corrections and improvements

## Content Quality Checklist

Before committing new content:

- [ ] Content is in AsciiDoc format (`.adoc` extension)
- [ ] Content is in English
- [ ] Page title is set with `= Title` syntax
- [ ] Structure follows pillar template (if applicable)
- [ ] Cross-references use `xref:` syntax with correct paths
- [ ] No relative paths (`../`) in xrefs
- [ ] No orphaned files or broken internal references
- [ ] Navigation updated in `modules/<pillar>/nav.adoc`
- [ ] Terminology is consistent with project glossary
- [ ] AsciiDoc syntax is valid

**Do not modify** unless coordinating with website repository maintainers.

### Cross-References

Use Antora xref syntax for all internal links:

```asciidoc
# Within the same module
xref:controls.adoc[Link text]

# With anchor
xref:controls.adoc#WAF-SEC-010[Link text]

# To another module
xref:pillar-security:controls.adoc[Security Controls]
xref:pillar-agentic:index.adoc[Agentic Pillar]

# With anchor in another module
xref:pillar-cost:controls.adoc#WAF-COST-010[Link text]
```

### Images and Assets

Place images in the module's `images/` directory:

```asciidoc
image::diagram.png[Alt text]
```

Antora will automatically resolve image paths during the build.

## Special Considerations

### Antora Integration

This repository is consumed as a **documentation component** by Antora:

- **Website repo**: https://github.com/WAF2p/waf2p.github.io
- **Build system**: Antora generates static HTML from this content
- **URL structure**: `https://waf2p.dev/docs/wafpp/1.0.1-en/<module>/<page-path>`
- **Version**: Currently `1.0.1-en` (defined in `antora.yml`)

### AsciiDoc vs Markdown

- **Use AsciiDoc** (`.adoc`), not Markdown
- AsciiDoc provides better semantic markup for technical documentation
- Antora requires AsciiDoc format
- See https://docs.asciidoctor.org/asciidoc/latest/ for syntax reference

### No Standalone Build

This repository **does not build independently**:
- No Jekyll configuration
- No build system in this repo
- Building happens in the parent website repository
- Content is sourced remotely or via filesystem by Antora

### Accessibility

When creating AsciiDoc content:
- Use semantic heading hierarchy (`=`, `==`, `===`)
- Provide alt text for images: `image::file.png[Descriptive alt text]`
- Ensure proper document structure
- Use Antora's built-in features for navigation and cross-referencing
